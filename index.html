PRIVACY ENGINEERING · ACADEMIC CASE STUDY

Privacy Engineering and Re-identification Risk Audit

I audited synthetic authentication and web logs, evaluated five pseudonymisation methods, and measured the balance between privacy protection and security-analysis utility.

PythonregexHMAC-SHA256SQLiteNginxDocker ComposeUbuntu
Project details & skills

Work completed

  • Deployed the academic environment using Ubuntu, VirtualBox and Docker Compose.
  • Configured a regex-based scanner to classify personal identifiers, quasi-identifiers and secrets, correcting false IPv4 detections caused by browser versions.
  • Minimized Nginx logging by removing URL parameters, Referer and User-Agent fields and truncating IP addresses.
  • Completed and tested Python functions for HMAC-SHA256 pseudonymisation, SQLite-backed static and daily tokenisation, and record minimisation.
  • Evaluated k-anonymity, uniqueness, profile linkability and distinct l-diversity.
  • Applied generalisation, weekly pseudonym rotation and iterative suppression.
  • Explored Laplace noise and contribution clipping in a differential privacy exercise.

Verified results in the academic environment

  • The initial partner export contained 3,539 events; 11.5% of persistent pseudonym profiles were unique.
  • Remediation achieved k ≥ 5 and l ≥ 2 while retaining 3,525 records and all 169 sensitive accesses.
  • A stricter configuration achieved k ≥ 10 and l ≥ 3 while retaining 3,487 records.

Scope & limitations

The thresholds apply to selected quasi-identifiers and do not prove anonymity. The differential privacy exercise has additional composition and publication limitations. These results demonstrate behavior in the academic scenario, rather than production-grade anonymisation or a complete differential privacy deployment.

Skills applied

Privacy-risk analysis; log minimisation; pseudonymisation and tokenisation; Python testing; k-anonymity and l-diversity evaluation; privacy–utility analysis; technical reporting.

Academic attribution & my contribution

Academic case study based on instructor-provided scenarios, datasets, infrastructure and skeleton code. Completed with AI-assisted Python implementations and guidance. My work included deployment, configuration, execution, troubleshooting, testing, evidence collection, interpretation and reporting.

NETWORK SECURITY · ACADEMIC CASE STUDY

Cross-Border Data Transfer Audit and Egress Control

I audited a simulated e-commerce application to discover undeclared destinations, inspect TLS and key-management arrangements, implement outbound controls, and document a Transfer Impact Assessment (TIA).

PythontsharkDocker ComposeOpenSSLTLS/X.509AES-GCMHMAC-SHA256nftablesUbuntu
Project details & skills

Work completed

  • Deployed a twelve-container environment using Docker Compose.
  • Captured application traffic with tshark and extracted destination IPs, TLS SNI, HTTP hosts and connection volumes.
  • Completed Python functions for TLS ClientHello parsing, longest-prefix GeoIP lookup and comparison against a declared transfer register.
  • Inspected TLS certificates and distinguished server-region information from certificate-holder identity.
  • Enabled client-side AES-256-GCM invoice encryption using the academic environment’s local KMS.
  • Configured gateway allow/block decisions and HMAC-based CRM pseudonymisation.
  • Applied nftables rules and tested direct connections that bypassed the proxy.
  • Produced a TIA discussing GDPR transfer requirements, Tunisian authorization requirements, residual risks and decisions by recipient.

Verified results in the academic environment

  • Identified eight initial destinations, four undeclared, including one using unencrypted HTTP.
  • Verified that stored invoices changed to the CSENC1 encrypted format and that the CRM received pseudonyms for names, emails and telephone numbers.
  • After confinement, 23 permitted application calls succeeded and 18 calls to undeclared destinations failed.
  • A direct blocked connection incremented the nftables rejection counter.

Scope & limitations

Countries, providers and certifications are simulated. Gateway decisions do not establish legal compliance. The Python parser does not reassemble TCP streams; HTTP payload evidence remains incomplete in the live CSV. The observed tests demonstrate controls in this academic environment, rather than production-wide enforcement or legal certification.

Skills applied

Traffic analysis; TLS and certificate inspection; transfer-register comparison; client-side encryption configuration; egress filtering; proxy-bypass testing; pseudonymisation; impact assessment and reporting.

PRIVILEGED ACCESS · ACADEMIC CASE STUDY

Privileged Access Management with SSH Certificates

I built and tested a containerized Privileged Access Management (PAM) environment on an Ubuntu VirtualBox VM using Docker Compose. The architecture included an SSH bastion, an OIDC identity provider, an administration workstation, and isolated application and PostgreSQL servers.

UbuntuVirtualBoxDocker ComposeOpenSSHSSH CAProxyJumpOIDCJWTPostgreSQLBashPython
Project details & skills

Architecture & access controls

I implemented Just-In-Time access using short-lived SSH certificates, with role-based principals, source-address restrictions and certificate validity limits. The containerized environment brought together bastion-based access, an OIDC identity provider and separate application and database targets.

Controls tested in the academic environment

  • Unauthorized-access rejection and certificate expiration.
  • Certificate revocation through an OpenSSH Key Revocation List (KRL).
  • Session recording and replay.
  • Command filtering for a restricted database role.

Troubleshooting & implementation

I troubleshot container startup, SSH account configuration, ProxyJump forwarding permissions and audit-log permissions, then documented the access-control behavior and security limitations.

Scope & limitations

These tests demonstrate access controls in an academic environment. Targets remained directly reachable from the Docker host, so the bastion was not an exclusive access path from that host. Audit logging also required tamper-resistant protection. The project does not establish production-grade isolation or audit integrity.

Skills applied

Privileged access management; Just-In-Time access; SSH certificate lifecycle management; role-based principals; bastion and ProxyJump configuration; revocation testing; session auditing; restricted-role command filtering; container troubleshooting; security documentation.
